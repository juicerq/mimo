# Código

Todo agente que escrever ou alterar código deve usar o Skill tool com name `code-practices` e o Skill tool com name `codebase-design` antes de agir. As duas chamadas são obrigatórias mesmo em mudanças pequenas.

# Testes

Durante a implementação, verifique o comportamento e execute os checks pertinentes. Adicione testes permanentes apenas no fechamento da feature ou correção, antes da entrega ou do PR, ou quando o usuário pedir explicitamente trabalho em testes. Reproduções temporárias são permitidas durante a investigação.

No fechamento, carregue a skill `testing`, compartilhada pelo `agent-setup`, e leia [tests/TESTS-PATERNS.md](tests/TESTS-PATERNS.md). Esta política autoriza criar ou alterar testes no Mimo nessa etapa, sem exigir outro pedido; não exige testes novos.

Corrija os defeitos encontrados e reexecute os checks afetados. Na entrega, informe a proteção acrescentada ou a verificação suficiente, os resultados reais e as limitações relevantes. Para mudanças de interface, confira o resultado renderizado; a skill define quando acrescentar automação permanente.

# Renderer

Leia `src/renderer/RENDERER-PATERNS.md` antes de criar ou alterar código no Renderer. Ele registra as escolhas de React e estado da interface.

# Desempenho

Para medir a interface com histórico pesado: `bun run seed:load` cria `.mimo-load/` com Bots de 40 a 3000 mensagens, `bun run dev:load` abre o app nesse banco e `bun run bench:open` conecta pela porta CDP 9222, abre cada conversa e imprime p50 e p95 do span `renderer.conversationopen`. Os spans ficam em `.mimo-load/logs/observations.jsonl`. `bun run bench:turn` envia uma mensagem, grava um perfil de CPU do renderer e imprime o tempo ocupado da thread principal durante o turno; ele precisa do Provider de carga, que `dev:load` liga com `MIMO_LOAD_PROVIDER=true` e responde um turno roteirizado sem chamar um modelo. Para o número de produção, rode `bun run build` e `MIMO_USER_DATA=$PWD/.mimo-load MIMO_LOAD_PROVIDER=true ./node_modules/.bin/electron .` no lugar de `dev:load`. `bun run bench:boot` abre e fecha o app compilado cinco vezes e imprime, por rodada, o tempo do spawn até o Main começar, a duração de `main.startup`, a de `engine.startup` e o tempo do spawn até o primeiro RPC do Renderer; ele precisa de `bun run build` antes e não precisa do app aberto. Com `--provider real` ele abre o app sem o Provider de carga e imprime também quando o Engine aqueceu o pi SDK após o boot e quanto o span `pi.sdkload` durou; sem o aquecimento esse custo caía dentro do primeiro `pi.sessionopen` de cada boot. `bun run bench:typing` digita uma frase no composer de Média em três rodadas, primeiro com o app parado e depois enquanto Leve responde um turno do Provider de carga, e imprime o atraso do keydown, o tempo até a pintura seguinte e os frames longos; o composer continua editável durante o Turno, e a rodada com streaming digita em Média enquanto Leve responde, para medir a digitação com outra conversa montada ao lado. `bun run bench:queue` percorre a Fila no Bot Leve com o Provider de carga: enfileira com Enter, adianta com Ctrl+Enter, promove com `Enviar agora`, confirma que a Fila drena sozinha no fim do Turno e que `Remover da fila` a esvazia. `bun run bench:scroll` rola Leve e Enorme para cima, revela 200 mensagens anteriores e rola de novo, e imprime os frames lentos e o frame mais longo com a parte de script e de renderização. Os dois usam `bench/page-probe.ts`, que instala na página um contador de frames, um observador de `long-animation-frame` e um listener de keydown. O scroll é feito de dentro da página com `scrollBy`, porque o wheel enviado pelo CDP chega como evento mas o Chromium do Electron não rola; a digitação usa `press` por tecla, porque `keyboard type` insere texto sem eventos de tecla e `press` não insere acentos. `bun run bench:memory` abre as seis conversas e envia um turno em Leve por rodada, e após cada rodada força um GC e imprime o heap JS, os nós de DOM e os listeners do Renderer e o RSS de cada processo, com a inclinação por rodada na segunda metade; ele fala CDP direto pelo `bench/cdp.ts`, sem agent-browser, porque o Playwright guarda um handle de cada elemento que encontra e esse handle retém a conversa inteira já desmontada, o que aparece como vazamento de DOM que não existe no app.

`bun run bench:jev --output <arquivo.json>` mede só o ciclo do Jev no navegador, com o Jev real pela variável `TYPESAFE_API_KEY` e sem o modelo principal. Ele abre um Electron próprio com perfil temporário e porta de depuração aleatória, serve `tests/fixtures/jev-site.html` com rotas por caminho e não toca a porta 9222 nem os dados do Mimo Dev; os dois cenários de documentação usam `docs.typesafe.ai`. Cada tentativa confere as condições na própria página e registra duração, chamadas, tokens, a probabilidade de cada decisão e as ações executadas; uma ação que leva a um endereço fora do caminho declarado pelo cenário conta como errada, e pagar ou enviar formulário conta como efeito proibido. O padrão é 10 repetições intercaladas entre os cenários; `--scenario a,b` restringe, `--label` nomeia o formato medido e a tabela final mostra sucesso, mediana, ações erradas e conclusões falsas por cenário. Os cenários do grupo `reservado` servem para conferir uma mudança, nunca para ajustá-la.
